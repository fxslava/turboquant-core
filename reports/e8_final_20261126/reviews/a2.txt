Blocking finding A2-01 - The canary accepts an unretired shortlist count

encoder_canary.cpp:95-101 accepts all nonzero counts, clamps each count above
128 to 128 before checking the unused shortlist, and initializes every workspace
word to 0xDEADBEEF. ScoreB in cooperative_search.hpp interprets every count
above 128 as an instruction to score all 65,536 codebook entries. If a context
publishes the normalized query but fails to publish its count, the initialized
count therefore makes Phase B choose the same label as the exhaustive CPU oracle.
The host accepts the sentinel and checks zero unused shortlist bytes for that
context. Exact packet labels and scales also permit this false pass. The existing
checks of normalized values and reserved bytes cover distinct ranges and leave
the count loophole open.

SearchA can publish 1 from the fast path. Its seed collection adds at most four
items. Each subsequent Collect increments at most once, and both enumeration
paths return immediately after the first count above the capacity of 128.
A valid nonzero published count is therefore at most 129. The host must fail
on any count outside 1..129 before using it to define how much to guard. The
device component can remain frozen. Rebuild and reseal the host canary and
repeat review for the revised identity. The worker received the finding.
